## 第一印象

作為軟體工程師，我寫過不少混亂的程式碼。我們都經歷過——在交付功能的壓力下，走捷徑，承諾自己「稍後再重構」。Robert C. Martin 的《無瑕的程式碼》正面解決了這個普遍的開發者經驗。

這不是一本關於演算法或設計模式的書。它是關於撰寫易於閱讀、理解和維護的程式碼的技藝。

## 核心收穫

### 1. 程式碼被閱讀的次數遠多於撰寫

Uncle Bob 強調，程式碼被閱讀的次數是撰寫次數的 10 倍。這個簡單的事實應該從根本上改變我們撰寫程式碼的方式。

與其優化撰寫速度，我們應該優化閱讀理解度。這意味著：
- 清晰的變數名稱而非簡短的
- 明確的邏輯而非聰明的技巧
- 解釋「為什麼」而非「是什麼」的註解

### 2. 函式應該只做一件事

單一職責原則應用於函式。一個函式應該做一件事，做好它，並且只做這件事。

我開始重構程式碼時會問：「這個函式做什麼？」如果我的答案中使用了「和」這個字，那它就做太多了。

**之前：**
```javascript
function processUserAndSendEmail(user) {
  validateUser(user);
  saveToDatabase(user);
  sendWelcomeEmail(user);
}
```

**之後：**
```javascript
function processUser(user) {
  validateUser(user);
  saveToDatabase(user);
}

function notifyUser(user) {
  sendWelcomeEmail(user);
}
```

### 3. 有意義的命名很重要

名稱應該揭示意圖。如果名稱需要註解，那就不是好名稱。

不好：`const d = 86400; // 一天的秒數`
好：`const SECONDS_IN_DAY = 86400;`

這看似顯而易見，但我無數次發現自己使用模糊的名稱，如 `data`、`result`、`temp`。現在我強迫自己要具體。

### 4. 童子軍規則

「讓程式碼比你發現時更乾淨。」

這深深引起我的共鳴。你不需要一次重構整個模組。即使是小改進——重新命名變數、提取函式、新增測試——隨著時間推移也會累積。

## 我不同意的地方

### 小函式可能過頭

Uncle Bob 提倡非常小的函式（3-5 行）。雖然我欣賞這個原則，但我發現過度使用會造成：
- 太多間接性（在數十個小函式之間跳轉）
- 更難除錯（堆疊追蹤變得笨重）
- 上下文遺失（難以看到大局）

我更喜歡小到一眼就能理解，但大到足以傳達完整思想的函式。

### 註解爭議

這本書建議註解通常是「無法在程式碼中表達自己的失敗」。雖然我同意程式碼應該自我說明，但我認為好的註解仍有一席之地：
- 解釋業務邏輯
- 記錄 API 契約
- 澄清不明顯的效能優化

註解應該解釋「為什麼」，而不是「是什麼」。

## 應用無瑕程式碼原則

這是我在工作流程中改變的事項：

1. **程式碼審查**：我現在更專注於可讀性而非聰明度。如果我需要思考兩次才能理解程式碼，我會要求修改。

2. **命名會議**：提交前，我會檢查所有變數和函式名稱。它們是否揭示意圖？新團隊成員能理解嗎？

3. **重構衝刺**：我在每個衝刺中專門投入時間改進現有程式碼，而不僅僅是增加功能。

4. **測試驅動開發**：先寫測試迫使我思考乾淨的介面。

## 最後的想法

《無瑕的程式碼》是一本我希望在職涯早期就讀過的書。它會讓我避免創造無數「聰明」的解決方案，而這些方案沒有人（包括未來的我）能理解。

**評分：4/5**

我扣了一顆星，因為有些範例感覺過時（大量 Java，冗長的 OOP 模式）。原則是永恆的，但程式碼範例可以更現代化。

**我會推薦嗎？** 絕對會，特別是對於有 2-5 年經驗的開發者。你已經寫了足夠的程式碼來理解 Uncle Bob 解決的痛點。

**最佳引言：**
> "事實上，閱讀與撰寫所花費的時間比率遠超過 10:1。我們不斷閱讀舊程式碼，作為撰寫新程式碼努力的一部分。因此，讓它易於閱讀就能讓它更容易撰寫。"

這本書不會讓你一夜之間成為更好的程式設計師。但它種下了種子，在數月和數年間成長為更好的習慣。
